# SOC2-BRIEF — Readiness, Honestly Split

**The one sentence an enterprise buyer needs:** SOC 2 is an audit of an *organization*, not a property of code — no commit can "make Pulse SOC 2 compliant." What code can do is supply the **product controls** an auditor probes and the **evidence on demand** that makes the organizational audit cheap. This brief maps the AICPA Trust Services Criteria onto Pulse in three honest columns: already shipped, built this session (SEC·D), and organizational work that only people and policies can do.

## Column 1 — Already shipped (prior gates, all tested)
CC6 logical access: RBAC with per-module read/write, department scoping enforced once in the CRUD rail, OIDC SSO (SAML refused at the schema level), forced password rotation, login rate limiting, auth_events trail with IP/UA. CC6.1 encryption: secrets at rest (SEC·A) with rotation scripts. C1/P confidentiality & privacy: data-subject erasure that anonymizes with a legal-retention registry, subject export, fault logs that record shape and hash but never payload contents (a test asserts this). CC7 monitoring: observability rail (W3·A), health honesty. Availability: instance export/restore with a corrected RESTORE_ORDER. Supply chain: nine production dependencies, enumerable.

## Column 2 — Built this session (SEC·D: audit integrity & access evidence)
**Tamper-evident audit log (CC7.2, CC4.1).** The governance trail becomes a hash chain: every row carries `seq`, `prevHash`, and `rowHash = sha256(prevHash | actor | action | entity | entityId | canonical(meta))`, appended through an in-process mutex (sound because deployment is one Node process per client instance — the instance-per-client architecture is itself the concurrency argument; a multi-process future would take a Postgres advisory lock, recorded here). Defense in depth: a database trigger makes `audit_log` **append-only** — UPDATE and DELETE raise, even for the application role — so the chain detects content/order tampering and the trigger blocks all mutation including timestamp edits. `GET /api/security/audit-verify` (admin-only) walks the chain and reports `{ok, checked, legacyRows, firstBreakSeq}` — pre-chain rows are declared as legacy, never silently blessed. **Design honesty:** `createdAt` is outside the hash (it is DB-assigned after the fact); its integrity rests on the trigger, and the brief says so rather than implying the chain covers it.

**Access review on demand (CC6.2/6.3).** `GET /api/security/access-review` returns every account with role, admin flag, active state, last successful login (from auth_events, refreshes excluded), and a **dormant** flag at 90 days — the quarterly user-access review an auditor asks for, generated live instead of assembled in a spreadsheet the night before. Surfaced on the System page with a one-tap chain verification.

**Evidence pack (`npm run soc2:evidence`).** A script that emits a dated markdown pack: dependency inventory with versions, table census, the product-control checklist verified by static inspection of the shipped code, and the organizational checklist below — so the gap list itself is a generated artifact, not a promise.

## Column 3 — Organizational, not code (do not let anyone pretend otherwise)
Security policy set and annual review · risk assessment · vendor management (Supabase, Vercel, Anthropic DPAs) · incident response runbook with tested restores · change management with a second reviewer — **the bus factor of one is a segregation-of-duties finding an auditor will write on day one**; it is recorded here as the top organizational risk, unsolved · background checks & security training · a monitoring/alerting on-call answerable by more than one person · and the audit itself: scope Type I first, Type II after a 3–6 month evidence window.

## Proof obligations (SEC·D tests)
Two audited actions chain correctly and verify `ok` · UPDATE and DELETE on audit_log both **raise** · with the trigger deliberately disabled by a superuser, a corrupted hash is caught at the exact `firstBreakSeq`, and repair restores `ok` · the demo seed's five sample audit rows are **declared as legacy exactly — never blessed — and no runtime writer can add to that count across the entire run** (this invariant caught a real hole on day one: the client portal wrote the trail through a raw INSERT, bypassing the chain; it now rides `logAuditSystem`, the trail's only other door) · access review is admin-only, flags a planted-dormant account, and counts admins · the whole prior suite stays green, proving the chain rides the existing fire-and-forget write path without breaking a single flow.
